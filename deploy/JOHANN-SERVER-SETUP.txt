Duranki: optional approved server setup

This is not the active GitHub Actions dev/test deployment contract. Do not change
workflows, automation or server configuration without explicit authorization.
Ordinary code releases do not require SSH. Production promotion is separate.

Read docs/MARIADB_ONLY.md and docs/IMPORTED_DATABASE_LOGIN.md before setup.

1. Obtain explicit server setup approval and verify Docker Compose support.
2. Provision private MariaDB and a restricted application user. Preserve existing
   databases; never delete tables or volumes to bypass startup validation.
3. Keep /srv/duranki/production.env private (mode 600). Configure DB_HOST,
   DB_PORT, DB_USER, DB_PASSWORD, DB_NAME, ID_PEPPER, JWT_SECRET and exact HTTPS
   origins. Preserve the existing identity pepper and encryption keys.
4. Supply matching MFA_ENCRYPTION_KEY (canonical base64 of 32 bytes) privately
   in production.env; metadata lives in MariaDB, not local keyfiles. Restore
   private uploads to /srv/duranki/uploads. Restrict access; the optional release
   image runs as UID/GID 1000. These mounts must be writable by that account.
5. Install and verify a real backup-before-release hook covering consistent
   MariaDB data plus keys, metadata and uploads. Test protected restoration.
6. After backup, approval and quiescing writers, use the candidate immutable
   image with compose.yml's maintenance-profile migrate service. It runs
   npm run migrate then npm run bootstrap. Failure must block deployment.
7. Use deploy-release.sh only after successful schema/bootstrap preparation.
   It replaces the app image, not database state. Rollback never undoes DB writes.
8. Verify HTTPS, exact-origin CORS, sign-in, MFA, registration persistence,
   tenant permissions, routes and assets. A healthy container is insufficient.

No server operation, private import or production deployment is performed by
these templates. Historical setup instructions do not supersede this contract.
