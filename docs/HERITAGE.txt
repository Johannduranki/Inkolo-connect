Duranki Heritage / Family Tree - first local release

> Historical implementation/results below are not current acceptance. Local-store
> setup and migration instructions are retired. Follow [MariaDB-only setup](MARIADB_ONLY.md).
> Preserve all existing security, privacy, authorization and payment-approval gates.
> Back up MariaDB, private uploads and matching MFA_ENCRYPTION_KEY before changes.


SETUP
Sign in normally, including MFA for administrators. Open Heritage from the
dashboard navigation or User Directory. As Platform Admin, choose an existing
tenant-linked community, open Service configuration, and enable both tenant and
community access. Tenant enablement applies to all that tenant's communities;
each community must also be enabled individually. Disabling either takes
effect immediately. No communities are enabled automatically.

The server trusts persisted membership tenant/community IDs, not browser
localStorage settings. Communities lacking a persisted tenant association
will not be offered. Existing legacy browser-only service toggles are not
authoritative for Heritage; use this service's configuration.

MEMBER WORKFLOW
Enabled communities appear in a Heritage section on member/community dashboards.
Platform administrators have a configuration entry on their platform dashboard.
Join Heritage records a community-specific subscription at R0/month. Creating
a tree or claiming an invitation also enrols the member atomically. Subscriptions
appear in the API and the user directory profile contribution breakdown.
Disabling tenant/community availability suspends the subscription and blocks
access without deleting family records. Existing accounts are not auto-enrolled.
Create family tree uses the signed-in member's own name to create a claimed,
Private person record. Add people; connect parent-to-child, spouse or sibling.
Grandparents, ancestors, descendants, aunts/uncles and first cousins are
derived from visible paths, not fixed father/mother fields. Select a person
or search the accessible list; zoom, pan, drag nodes and fit the graph.
Relationship kinds include biological, adoptive, step and unspecified.
Succession is not used in family path calculations.

DUPLICATES
Normalized name matching is offered before creation. An identical normalized
name and birth date blocks creation unless a reviewed distinct-person reason
is supplied and recorded. This is a warning/review process, not identity
verification or an automatic merge. Cross-tree merges are not implemented.

PRIVACY
Private: profile manager only; no general administrator override.
Family: claimed participants in the same tree and the profile manager.
Community: authenticated members in the same tenant/community; scoped
administrators can inspect it.
Public: authenticated community access plus an anonymous minimal summary
endpoint containing display name, birth/death years and verification status.
Notes, documents, contact details and relationships are not publicly exposed.
Unclaimed living relatives cannot be made Public. Unclaimed deceased persons
may be published by their manager. All people default to Private.

INVITATIONS
Invite by a registered relative's phone number. The account must be active
and belong to this community. The invitee can accept or decline in the Family
invitations inbox. Alternatively, share the generated code privately and use
Claim an invited profile. There is no automatic SMS/email delivery.
Tokens are hashed, targeted, one-use, expire after seven
days, and are revoked when reissued. Claiming transfers profile management
and resets privacy to Private and verification to Unverified.
